## 1. 全景：一个请求怎么走完

```
浏览器 / uni-app
   │  uni.request({ url: 'http://localhost:3000/api/dishes?keyword=牛' })
   ▼
Express 进程（node server/app.js）
   │
   ├─ cors()            允许跨域
   ├─ express.json()    解析请求体
   ├─ 日志中间件         记录方法、路径、状态码、耗时
   │
   ├─ /api/dishes ──► routes/dishes.js ──► store.dishes() ──► data/db.json
   │
   └─ 其他 GET ────► public/index.html（前端页面）
   ▼
res.json({ total, categories, items })
```

目录与职责：

```
实验六/
├── server/
│   ├── app.js          入口：中间件 → 路由 → 静态托管 → 兜底
│   ├── store.js        数据层：读写 db.json，原子写
│   ├── seed.json       种子数据（12 道菜 + 分类）
│   └── routes/
│       ├── dishes.js   菜品与评论（4 个接口）
│       └── favorites.js 收藏（3 个接口）
├── data/db.json        运行时生成的数据文件
├── public/             打包好的前端（H5 产物）
└── client/             uni-app 源码（实验四的副本 + 接口改造）
```

> **本节知识点**
>
> | 知识点 | 一句话 |
> | --- | --- |
> | 前后端分离 | 前端只管渲染，数据通过 HTTP 接口取 |
> | 请求-响应模型 | 一次请求对应一次响应，状态码表示结果类别 |
> | 中间件管道 | 请求按注册顺序穿过一串函数，每个都能改写或提前结束 |
> | 端口与同源 | 后端 3000、前端开发时 8080，端口不同就是跨域 |

## 2. 入口 `server/app.js`

### 2.1 中间件的顺序

```js
const app = express()

app.set('json spaces', 2)                        // 接口返回带缩进
app.use(cors())                                  // ① 跨域
app.use(express.json({ limit: '64kb' }))         // ② 解析请求体
app.use((req, res, next) => { /* 日志 */ next() })  // ③ 记日志
app.use('/api/dishes', dishesRouter)             // ④ 业务路由
```

顺序不能随便换：**`express.json()` 必须在读 `req.body` 之前**，否则 `req.body` 是 `undefined`；
日志中间件放在路由前面，才能把每个请求都记下来（包括 404 的）。

`limit: '64kb'` 是给请求体设上限。不设的话，有人发一个 100MB 的 JSON，服务端会先把它整个读进内存。

### 2.2 静态托管与 SPA 兜底

```js
const PUBLIC_DIR = path.join(__dirname, '..', 'public')

app.use(express.static(PUBLIC_DIR))

// 不是 /api 开头的 GET，一律返回 index.html
app.use((req, res, next) => {
  if (req.method !== 'GET' || req.path.startsWith('/api')) return next()
  res.sendFile(path.join(PUBLIC_DIR, 'index.html'), (error) => { if (error) next() })
})
```

为什么需要兜底？因为 uni-app 的 H5 是**前端路由**：`/#/pages/detail/index?id=2` 这种地址，
服务器上并不存在 `pages/detail/index` 这个文件。刷新页面时浏览器会真的去请求这个路径，
没有兜底就 404 了。

### 2.3 兜底 404 与错误处理

```js
// 走到这里说明既不是接口，也没有对应文件
app.use((req, res) => {
  res.status(404).json({ error: { code: 'NOT_FOUND', message: `找不到 ${req.method} ${req.originalUrl}` } })
})

// 四个参数才是错误处理中间件，Express 靠参数个数识别
app.use((error, req, res, next) => {
  if (error.type === 'entity.parse.failed') {
    return res.status(400).json({ error: { code: 'BAD_JSON', message: '请求体不是合法的 JSON' } })
  }
  console.error('[error]', error)
  res.status(500).json({ error: { code: 'INTERNAL_ERROR', message: '服务器开小差了，稍后再试' } })
})
```

**错误处理中间件必须写四个参数**，少一个 Express 就当成普通中间件，异常永远进不来。

> **本节知识点**
>
> | 知识点 | 一句话 |
> | --- | --- |
> | 中间件与 `next()` | 调用 `next()` 才继续往下走，不调用就停在这里 |
> | 中间件顺序 | 按 `app.use` 的注册顺序执行，解析体必须在使用体之前 |
> | `express.static` | 把目录映射成静态文件服务 |
> | SPA 兜底 | 前端路由的路径在服务器上不存在，需要回退到 index.html |
> | 错误中间件 | 四个参数 `(err, req, res, next)`，只能捕获同步异常和 `next(err)` |
> | `res.status().json()` | 一次设状态码并返回 JSON |

## 3. 数据层 `server/store.js`

### 3.1 为什么用 JSON 文件

课程作业的数据量只有 12 道菜，装 MySQL 要额外起服务、配账号、写建表语句，
成本远大于收益。一个 `db.json` 能直接打开看、能拷走、能进 git。

代价也说清楚：**没有并发控制**。两个人同时发评论，后写的会覆盖先写的。
真实项目里这一步必须交给数据库。

### 3.2 内存缓存 + 懒加载

```js
let db = null

function load() {
  if (db !== null) return db          // 已经读过就直接返回，不重复读盘
  fs.mkdirSync(DATA_DIR, { recursive: true })
  if (fs.existsSync(DB_FILE)) {
    db = JSON.parse(fs.readFileSync(DB_FILE, 'utf8'))
  } else {
    db = readSeed()                    // 首次启动：用种子数据初始化
    save()
  }
  return db
}
```

整个进程只有一份 `db`，所有接口都读写它。这样既避免每次请求都读文件，
也保证「改完立刻能读到」——因为读的就是同一份内存对象。

### 3.3 原子写

```js
function save() {
  const tmp = `${DB_FILE}.tmp`
  fs.writeFileSync(tmp, JSON.stringify(db, null, 2), 'utf8')
  fs.renameSync(tmp, DB_FILE)          // 改名是原子操作
}
```

如果直接 `writeFileSync(DB_FILE, ...)`，写到一半进程被杀，文件就只剩半截 JSON，
下次启动直接解析失败，数据全丢。先写临时文件再改名，**要么是旧文件、要么是新文件，不会出现半个**。

### 3.4 坏文件自愈

```js
try {
  db = JSON.parse(fs.readFileSync(DB_FILE, 'utf8'))
} catch (error) {
  const backup = `${DB_FILE}.broken-${Date.now()}`
  fs.renameSync(DB_FILE, backup)       // 坏的留证据
  db = readSeed()                      // 用种子重建
  save()
}
```

宁可丢数据也要让服务起来——这是可用性优先的选择。把坏文件改名备份，而不是删掉，
出问题时还能人工抢救。

### 3.5 收藏的存储结构

```js
favorites: {
  "dev-l66c3ki1": [2, 5],     // 设备号 → 菜品 id 数组
  "dev-9x2m0pqa": [1]
}
```

以设备号为键，值是 id 数组。这个结构决定了接口形状：`GET /api/favorites` 返回 `ids`，
`PUT /api/favorites/:id` 往数组里加。

> **本节知识点**
>
> | 知识点 | 一句话 |
> | --- | --- |
> | 模块级单例 | `let db` 在模块顶层，整个进程共享一份 |
> | 懒加载 | 第一次用到才读盘，避免启动时阻塞 |
> | 原子写 | 写临时文件 + `rename`，避免半个文件 |
> | 容错与降级 | 解析失败不抛给用户，备份后重建 |
> | JSON 作为存储 | 简单直观，但没有并发控制与索引 |
> | 数据建模 | 用「设备号 → id 数组」表达一对多关系 |

## 4. 路由 `server/routes/dishes.js`

### 4.1 列表：筛选、排序都在服务端

```js
const SORTS = {
  rating: (a, b) => b.rating - a.rating,
  priceAsc: (a, b) => a.price - b.price,
  priceDesc: (a, b) => b.price - a.price
}

router.get('/', (req, res) => {
  const keyword = String(req.query.keyword || '').trim()
  const category = String(req.query.category || '全部')
  const sort = String(req.query.sort || 'default')

  let list = store.dishes()
  if (category !== '全部') list = list.filter((d) => d.category === category)
  if (keyword !== '') {
    const word = keyword.toLowerCase()
    list = list.filter((d) =>
      d.name.toLowerCase().includes(word) ||
      d.desc.toLowerCase().includes(word) ||
      d.canteen.toLowerCase().includes(word) ||
      d.tags.some((t) => t.toLowerCase().includes(word)))
  }
  if (SORTS[sort]) list = [...list].sort(SORTS[sort])

  res.json({ total: list.length, categories: store.categories(), items: list })
})
```

两个细节值得注意：

- **`SORTS[sort]` 是查表，不是拼字符串。** 如果写 `eval` 或者动态函数名，用户传个奇怪的值就能执行任意代码。
- **`[...list].sort()` 先复制。** `sort` 会原地改数组，不复制的话会把 `store` 里的顺序也改掉，
  下一次请求默认排序就乱了。

### 4.2 参数校验：先校验，再进存储层

```js
function parseId(raw) {
  const value = Number(raw)
  return Number.isInteger(value) && value > 0 ? value : null
}

router.post('/:id/comments', (req, res) => {
  const id = parseId(req.params.id)
  if (id === null) return badRequest(res, 'id 必须是正整数')

  const content = String(req.body.content || '').trim()
  const rating = Number(req.body.rating)

  if (content.length < 5) return badRequest(res, '评论内容至少 5 个字')
  if (!Number.isInteger(rating) || rating < 1 || rating > 5) {
    return badRequest(res, '评分必须是 1 到 5 的整数')
  }

  const created = store.addComment(id, { name, rating, content })
  if (created === null) {
    return res.status(404).json({ error: { code: 'DISH_NOT_FOUND', message: '没有这道菜' } })
  }
  res.status(201).json(created)
})
```

`req.params.id` **永远是字符串**，`'2' !== 2`，所以要 `Number()` 转换并验证。
校验放在最前面，任何一项不合法就直接返回，不浪费后面的查询和写盘。

状态码的语义也要对：新建成功用 **201**，参数错 **400**，资源不存在 **404**，服务端异常 **500**。

> **本节知识点**
>
> | 知识点 | 一句话 |
> | --- | --- |
> | RESTful 资源命名 | 用名词表示资源（`/dishes/:id`），用方法表示动作 |
> | 查询参数 | `req.query` 读 `?keyword=牛` 这类参数，值都是字符串 |
> | 路径参数 | `req.params.id` 也是字符串，要自己转数字 |
> | 白名单 | 排序方式查表，不接受任意字符串 |
> | 不可变操作 | 排序前先复制数组，避免改到共享数据 |
> | 状态码语义 | 201 创建 / 400 参数错 / 404 不存在 / 500 服务器错 |
> | 参数校验 | 在进入业务逻辑前把非法输入挡掉 |

## 5. 路由 `server/routes/favorites.js`

### 5.1 没有登录，怎么区分设备

```js
function deviceIdOf(req) {
  const raw = String(req.get('x-device-id') || '').trim()
  return /^[A-Za-z0-9-]{6,64}$/.test(raw) ? raw : 'anonymous'
}
```

前端首次启动生成一个 `dev-xxxxxxxx` 存在本地，之后每次请求放在请求头里。
服务端用它当「用户标识」。

**这是个权宜之计**：换设备就看不到原来的收藏，请求头也能被伪造。
真实项目必须做登录，用会话或 JWT 识别用户。

正则那一步不是多余的：这个值会被当成 JSON 的**键**写进文件，
不做白名单的话，一个奇怪的字符串就能把数据结构搞乱。

### 5.2 幂等：PUT 加、DELETE 删

```js
router.put('/:id', (req, res) => {
  const added = store.addFavorite(deviceId, id)
  res.status(added ? 201 : 200).json({ added, ids: store.favoritesOf(deviceId) })
})

router.delete('/:id', (req, res) => {
  const removed = store.removeFavorite(deviceId, id)
  res.json({ removed, ids: store.favoritesOf(deviceId) })
})
```

为什么不用 `POST /favorites/toggle`？因为 toggle 的结果依赖「当前是什么状态」：
网络重试一次，可能加了又删。而 PUT/DELETE 是**幂等**的——调用一次和调用十次结果一样，
网络不稳定时重试不会出问题。

`added` 为 `false` 表示本来就收藏了，这时返回 200 而不是 201，语义更准确。

> **本节知识点**
>
> | 知识点 | 一句话 |
> | --- | --- |
> | 自定义请求头 | `x-device-id` 携带设备标识 |
> | 输入白名单 | 正则限制字符集和长度，防止污染存储的键 |
> | 幂等性 | PUT/DELETE 重复调用结果一致，适合重试 |
> | 201 vs 200 | 真正新建了才用 201 |
> | 无状态服务 | 服务端不记会话，每个请求自带身份信息 |

## 6. 前端改造 `client/utils/`

### 6.1 `config.js`：只有一个常量

```js
export const BASE_URL = 'http://localhost:3000'
```

单独抽出来是因为它**因环境而异**：浏览器里是 localhost，真机要改成电脑的局域网 IP，
上线要改成域名。集中在一处，换环境只改一行。

### 6.2 `api.js`：为什么不用 fetch

```js
export function request(path, options = {}) {
  return new Promise((resolve, reject) => {
    uni.request({
      url: `${BASE_URL}/api${path}`,
      method: options.method || 'GET',
      data: options.data,               // GET 时会被拼成查询字符串
      timeout: 8000,
      header: { 'x-device-id': deviceId(), 'content-type': 'application/json' },
      success(response) {
        const body = response.data
        if (response.statusCode >= 200 && response.statusCode < 300) {
          resolve(body)
          return
        }
        // 后端统一返回 { error: { code, message } }
        const message = (body && body.error && body.error.message) || `请求失败（${response.statusCode}）`
        reject(new Error(message))
      },
      fail() {
        reject(new Error('连不上服务器，确认后端已经启动（npm start）'))
      }
    })
  })
}
```

**小程序里没有 `fetch`，也没有 `XMLHttpRequest`**，只有 `uni.request`。
而且它的回调是 `success/fail` 而不是 Promise，所以要自己包一层。

包这一层解决三件事：
1. 拼前缀（`BASE_URL + /api`），页面里只写 `/dishes/2`；
2. 自动带设备号；
3. 把 HTTP 错误码和网络失败统一成 `reject(new Error(可读的中文))`，页面只写 `try/catch`。

注意 `success` 里**状态码 4xx/5xx 也算成功回调**（TCP 层通了），必须自己判断。

### 6.3 `useDishes.js`：一份数据三个页面用

```js
const state = reactive({ dishes: [], categories: ['全部'], loading: false, error: '', loaded: false })

async function load(force = false) {
  if (state.loading) return          // 防重复请求
  if (state.loaded && !force) return // 已加载过就不再请求

  state.loading = true
  state.error = ''
  try {
    const data = await api.get('/dishes')
    state.dishes.splice(0, state.dishes.length, ...data.items)  // 原地替换，保留响应式
    state.categories = data.categories
    state.loaded = true
  } catch (error) {
    state.error = error.message
  } finally {
    state.loading = false
  }
}
```

`splice(0, length, ...items)` 而不是 `state.dishes = items`：
保持数组引用不变，所有已经引用它的 `computed` 都能继续工作。

### 6.4 `useFavorites.js`：乐观更新

```js
async function toggleFavorite(id) {
  const index = favoriteIds.indexOf(id)
  const adding = index === -1

  if (adding) favoriteIds.push(id)      // 1. 先改界面
  else favoriteIds.splice(index, 1)

  try {
    if (adding) await api.put(`/favorites/${id}`)   // 2. 再发请求
    else await api.del(`/favorites/${id}`)
  } catch (error) {
    // 3. 失败回滚
    if (adding) {
      const back = favoriteIds.indexOf(id)
      if (back > -1) favoriteIds.splice(back, 1)
    } else {
      favoriteIds.push(id)
    }
    throw error                          // 交给页面弹提示
  }
}
```

如果等请求回来再变色，点一下要等半秒才有反馈。
先改本地再发请求叫**乐观更新**——假设请求会成功。失败时必须回滚，否则界面和服务器就对不上了。

`throw error` 是刻意的：这一层只负责状态，提示交给页面，因为它知道该说什么话。

> **本节知识点**
>
> | 知识点 | 一句话 |
> | --- | --- |
> | 环境配置抽离 | 地址因环境而异，集中成一个常量 |
> | 请求封装 | 统一前缀、鉴权头、错误处理 |
> | `uni.request` | 四端通用的请求 API，回调式，不是 Promise |
> | Promise 包装 | 把回调式 API 转成 `await` 能用的形式 |
> | 响应式数组替换 | `splice` 原地替换，保留引用 |
> | 防重复请求 | `loading` 标记 + `loaded` 缓存 |
> | 乐观更新 | 先改界面再发请求，失败回滚 |

## 7. 三个页面改了什么

### 7.1 首页 `pages/home/index.vue`

```js
const remoteStats = ref({ dishes: 0, canteens: 0, averageRating: 0, comments: 0 })

onMounted(() => {
  load()            // GET /api/dishes
  loadStats()       // GET /api/stats
  loadFavorites()   // GET /api/favorites
})

const stats = computed(() => [
  { label: '收录菜品', value: remoteStats.value.dishes, unit: '道' },
  { label: '覆盖食堂', value: remoteStats.value.canteens, unit: '个' },
  { label: '平均评分', value: Number(remoteStats.value.averageRating).toFixed(1), unit: '分' },
  { label: '我的收藏', value: total.value, unit: '道' }
])
```

三个请求并发发出（没有互相 `await`），谁先回来先渲染。
模板里加了三种状态：`loading` 转圈、`error` 显示提示条 + 重试、有数据才渲染主体。

`todayPick` 也加了空数组判断——数据还没回来时 `state.dishes.length === 0`，
直接取模会得到 `undefined`，`HeroBanner` 读 `pick.gradient` 就崩了。

### 7.2 菜单页 `pages/menu/index.vue`

```js
let debounceTimer = null
watch([keyword, category, sortIndex], () => {
  clearTimeout(debounceTimer)
  debounceTimer = setTimeout(fetchList, 300)
})
```

**防抖**：输入框每敲一个字都发请求，打 10 个字就是 10 次请求。
等用户停下来 300 毫秒再发，通常只剩 1 次。

```js
const filteredDishes = computed(() => {
  if (!onlyFavorite.value) return list.value
  return list.value.filter((dish) => isFavorite(dish.id))
})
```

为什么「只看收藏」还在前端筛？因为收藏是一组 id，属于另一个资源。
为了一个开关再去请求一次接口不划算——把 id 列表和后端返回的列表取交集就够了。

### 7.3 详情页 `pages/detail/index.vue`

```js
onLoad((options) => {
  dishId.value = Number(options.id || 0)
  loadDish()      // GET /api/dishes/:id（评论一起返回）
  load()          // 同类推荐要用整个列表
  loadFavorites()
})

async function addComment(payload) {
  try {
    const created = await api.post(`/dishes/${dishId.value}/comments`, payload)
    comments.value.unshift(created)     // 用服务端返回的那条，不自己拼
    show('评论已发表，谢谢分享')
  } catch (requestError) {
    show(requestError.message)
  }
}
```

发评论成功后**用服务端返回的对象**插入列表，而不是把表单内容拼一条假的。
服务端可能补了 `id`、改了 `time`、做了 trim——以服务端为准，界面和存储才一致。

> **本节知识点**
>
> | 知识点 | 一句话 |
> | --- | --- |
> | 并发请求 | 互不依赖的请求不必串行 `await` |
> | 三态渲染 | 加载中 / 失败 / 成功，缺一个用户就会看到白屏 |
> | 空值保护 | 数据未到时先判断长度，避免取到 undefined |
> | 防抖 | 停止输入一段时间后才触发，减少请求 |
> | 混合筛选 | 服务端筛大集合，客户端做本地集合的交集 |
> | 以响应为准 | 写操作后用服务端返回的数据更新界面 |

## 8. 三条数据流

### ① 搜索：从键盘到服务端

```
用户输入「牛」
  → SearchBar emit('update:modelValue', '牛')
  → keyword 变化 → watch 触发 → 300ms 后 fetchList()
  → GET /api/dishes?keyword=牛&category=全部&sort=default
  → 服务端 filter → 返回 1 条
  → list.value = data.items → v-for 重渲染
```

### ② 收藏：一次点击，两个地方改

```
点爱心
  → favoriteIds 立刻 +1（界面马上变红）
  → PUT /api/favorites/2（带 x-device-id）
  → 成功：什么都不用做，界面已经是新状态
  → 失败：回滚 favoriteIds，弹「连不上服务器」
```

### ③ 评论：写操作的三步

```
提交表单
  → POST /api/dishes/2/comments
  → 服务端校验 → 写入 db.json → 返回 201 + 新评论
  → 前端 unshift 到列表头部 + 弹提示
  → 刷新页面 / 重启服务，这条评论仍在（因为落盘了）
```

> **本节知识点**
>
> | 知识点 | 一句话 |
> | --- | --- |
> | 单向数据流 | 输入 → 状态 → 请求 → 响应 → 视图，不手动操作 DOM |
> | 乐观更新 | 先改状态提升体验，失败再回滚 |
> | 写后读一致性 | 写操作以服务端返回为准，避免本地和服务端不一致 |
> | 持久化 | 内存改了必须落盘，否则重启就丢 |

## 10. 讲的时候怎么串（30 秒版）

> 实验六是给实验四的前端加后端。后端用 Express，九个接口，数据存在 `db.json` 里。
> 入口 `app.js` 按顺序挂中间件：跨域、解析 JSON、记日志，然后挂路由，最后托管前端页面。
> 数据层 `store.js` 只有一份内存副本，每次改完写盘，写盘用临时文件加改名保证原子性。
> 接口设计上，筛选排序做成列表接口的查询参数，收藏用 PUT/DELETE 保证幂等，
> 设备号放在请求头里区分「谁的收藏」。
> 前端加了一层 `api.js` 封装 `uni.request`，因为小程序没有 fetch；
> 收藏用乐观更新，先改界面再发请求，失败回滚。
> 验证的时候发完评论重启服务，数据还在——说明确实落盘了。

### 老师可能追问

**Q：为什么不用数据库？**
A：数据量小，装 MySQL 的成本大于收益。代价是没有并发控制，两个人同时写会覆盖，真实项目必须换。

**Q：没有登录怎么区分用户？**
A：请求头带一个本地生成的设备号。这是权宜之计，换设备就丢，请求头也能伪造，真实项目要用 JWT 或会话。

**Q：为什么收藏不用 POST /toggle？**
A：toggle 依赖当前状态，网络重试可能加了又删。PUT/DELETE 是幂等的，重复调用结果一样。

**Q：`express.json()` 漏了会怎样？**
A：`req.body` 是 `undefined`，读 `req.body.content` 直接抛异常，接口 500。

**Q：为什么错误处理中间件要四个参数？**
A：Express 靠函数参数个数区分普通中间件和错误中间件，少一个就永远进不去。

**Q：前端为什么不用 fetch？**
A：小程序里没有 fetch，只有 `uni.request`；而且它是回调式的，要自己包成 Promise。

**Q：如果两个人同时发评论会怎样？**
A：会丢一条。`store` 是读-改-写，中间没有锁；这是 JSON 文件存储的固有限制。

**Q：数据文件被写坏了怎么办？**
A：启动时解析失败会改名备份，然后用 `seed.json` 重建，保证服务能起来。
